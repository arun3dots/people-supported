# Deliverable 5 – Security and privacy threat assessment

Threats specific to a multi-tenant care-home platform. **Confirmed** = reproduced from code reading; **Potential** = plausible given the evidence; **Unverified** = depends on infrastructure not visible in the repository. Residual risk is rated after existing controls, before remediation.

| # | Threat | Attack scenario | Affected assets | Existing controls (cited) | Status | Residual risk | Mitigation (finding IDs) | Verification test |
|---|---|---|---|---|---|---|---|---|
| T1 | Cross-tenant resident data exposure | Carer at Home A obtains a resident UUID from Home B (shared screenshot, support ticket, leaked export) and calls `GET /api/observations/resident/{uuid}` or `POST /api/observations` with that `residentId`. | Observations (NEWS2 vitals, ACVPU), resident name via escalation notifications | `tenantId` from JWT enforced in most modules (`AGENTS.md` rule 5; `residents.findOne` where `{id, tenantId}`); **observations module has none** (`observations.service.ts:11-13, 145, 151-156`); UUIDs are unguessable but not secret | **Confirmed** | High | D-07, D-08, E-14: pass tenantId to all observation queries; repository-level guard; cross-tenant e2e tests | Seed two tenants; authenticate as tenant A; read/create observation for tenant B resident → expect 404/403 |
| T2 | Privilege escalation by care staff | Carer calls routes their UI hides: `GET /api/audit-logs` (JwtAuthGuard only, `audit.controller.ts:44`) to read colleagues' activity; Nurse hard-deletes a medication round (`medications.controller.ts:108`). | Audit metadata, eMAR history | RolesGuard/PermissionsGuard on 32/36 controllers; audit DB immutable | **Confirmed** (read); **Potential** (misuse) | Medium | D-06, C-07, B-06: role-restrict audit listing; soft-delete with reason | Role-matrix e2e: Carer → `/audit-logs` expect 403 |
| T3 | Compromised staff account (phishing / credential stuffing) | Attacker tries leaked passwords against `/api/auth/login`; no throttle or lockout; MFA not enforced; 8-char minimum. | All resident and staff data in the tenant | bcrypt hashing; cookie HttpOnly; FAILED_LOGIN audit type defined but no alerting | **Confirmed** (controls absent) | High | D-01, D-02, D-12, E-05 | 100 requests/10 s to login → expect 429 and FAILED_LOGIN alert; login without MFA for Admin → expect block |
| T4 | Forged tokens via default secret | Deployment or new environment without `JWT_SECRET`; backend and web middleware both default to `'secretKey'`; attacker mints a SuperAdmin token. | Entire platform | None (fallback is silent) | **Potential** (depends on env hygiene) | High | D-04: fail closed; secret length check; rotate | Start app without `JWT_SECRET` → expect crash |

| T7 | Disclosure through logs, backups, exports, third parties | Resident names in push payloads via FCM/web-push; `console.log` of user objects (RolesGuard); client GPS stored permanently; backups of unknown location/encryption; Swagger public. | Names + clinical context; staff location; backup media | SecureStore on mobile; GCS authenticated streams | **Confirmed** (payload/log content); **Unverified** (backups) | Medium | C-09, E-09, E-10, E-16, A-09 | Inspect a push payload → no resident name; grep console.log in guards → 0 |
| T8 | Ransomware / service unavailability | Single VM (`ecosystem.config.js`, PM2) compromised or disk lost; no documented backup/restore, no offline MAR fallback. | Availability of eMAR and care plans across all tenants | PM2 autorestart; Renovate updates; backups asserted only | **Unverified** | High (safety impact) | E-10, I-06, E-08, E-12 | Restore test from backup into clean environment within target RTO; print fallback pack generated |
| T9 | Improper AI processing of resident information | Future feature sends care notes to an external LLM without DPIA/contract. | Special-category data | No AI/LLM dependency today (`care-plan-auto-draft.service.ts` is template-based) | Not present | Low now | H-03, A-09 (screening question) | Dependency scan for AI SDKs in CI |
| T10 | Inadequate incident response | Breach discovered by a carer; no owner, no 72-hour clock, no path to notify tenant controllers; no log aggregation to scope the breach. | Regulatory exposure for tenants and vendor | None | **Confirmed** (absent) | High | E-17, E-09, D-12 | Tabletop exercise completes assessment and tenant notification inside 24 h |
| T11 | Inappropriate retention or disposal | Enquiry health notes, discharged residents, expired tokens and GPS trails kept forever; no appraisal or destruction evidence; or, conversely, ad-hoc deletion of records under legal hold. | All data | None (no retention job; `deletedAt` soft delete on some models) | **Confirmed** (absent) | Medium | B-10, B-07, C-10, H-05 | Retention job flags seeded 9-year-old record for appraisal; legal-hold record resists purge |

| T15 | Staff location surveillance | GPS captured on every page view into an immutable log; no purpose, notice or opt-in; cannot be erased. | Staff privacy; employment-law exposure for tenants | Coordinates sanity-checked only | **Confirmed** | Medium | A-09, C-09, A-04 | Feature off by default; DPIA covers it or it is removed |

## Notes on likelihood

- T1 requires knowledge of a foreign UUID. UUIDs appear in URLs, exports, notifications and support conversations, so this is not a strong barrier; the control is simply absent.
- T4 and T6 (empty keys) are configuration-dependent. The CI workflow already uses the published placeholder encryption key, which shows how easily the fallback path is exercised.
- T8 is rated High because of safety impact rather than probability: medication rounds depend on the system being up and there is no documented fallback.
